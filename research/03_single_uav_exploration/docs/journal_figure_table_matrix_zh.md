# 期刊图表反推与正式实验冻结方案

## 1. 文档目的

本文件不是规定“怎样把现有截图修漂亮”，而是从代表性的无人机自主探索论文反推：

1. 一篇自主探索与三维建图小论文需要哪些证据；
2. 每幅图和每张表分别回答什么审稿问题；
3. 为生成这些图表，每次实验开始前必须具备哪些数据记录能力；
4. 哪些运行属于正式实验，哪些只能算调试或校准。

核心原则是：

> 先冻结研究问题、对照方法、指标、数据字段和失败规则，再运行实验。实验结束后不得根据结果临时更换指标、边界、阈值或挑选最好的一次运行。

## 2. 代表性论文实际采用的图表

### 2.1 FUEL：单无人机快速自主探索

文献：

- B. Zhou, Y. Zhang, X. Chen, and S. Shen, “FUEL: Fast UAV Exploration Using Incremental Frontier Structure and Hierarchical Planning,” IEEE Robotics and Automation Letters, 2021.
- IEEE 页面：https://ieeexplore.ieee.org/document/9324988/
- 作者公开稿：https://repository.hkust.edu.hk/ir/bitstream/1783.1-108720/1/033635_1.pdf

FUEL 的实验部分不是只展示最终地图，而是组合使用：

| 证据 | 文献中的形式 | 证明的问题 |
|---|---|---|
| 仿真环境与完整轨迹 | Fig. 7、Fig. 9 | 方法是否在相同场景中产生更合理、更少回访的路径 |
| 探索进度曲线 | Fig. 8 | 已探索空间是否随时间更快增长 |
| 实验场景、在线地图和轨迹 | Fig. 1、Fig. 10、Fig. 11 | 系统是否能够在真实复杂环境中在线自主工作 |
| 探索统计表 | Table II | 探索时间和飞行距离的 Avg、Std、Max、Min |
| 模块计算时间表 | Table III | Frontier、视点、全局规划、局部规划、轨迹生成是否满足实时性 |

FUEL 在两个仿真场景中对每种方法重复 3 次，并保持相同初始条件、速度上限、偏航速度、传感器视场和量程。由此可得：

- 单张最终地图不能替代探索进度曲线；
- 一次成功运行不能替代重复统计；
- 轨迹图用于解释“为什么更快”，统计表用于证明“确实更快”；
- 计算时间是自主规划论文的必要证据，不是可选装饰。

### 2.2 RACER：多无人机协同探索

文献：

- B. Zhou, H. Xu, and S. Shen, “RACER: Rapid Collaborative Exploration with a Decentralized Multi-UAV System.”
- 公开稿：https://arxiv.org/pdf/2209.08533

RACER 的图表比 FUEL 增加了协同、规模和通信证据：

| 证据 | 文献中的形式 | 证明的问题 |
|---|---|---|
| 系统框架图 | Fig. 2 | 感知、协调、规划和控制如何连接 |
| 在线任务结构示意 | Fig. 3--9 | 未知空间如何在线形成任务，而非提前规划路线 |
| 消融过程图 | Fig. 10 | 去掉全局覆盖引导后为什么出现重复访问 |
| 多方法轨迹对比 | Fig. 11 | 不同协同方法是否造成路径交叉和重复探索 |
| 无人机数量与进度曲线 | Fig. 12、Fig. 13 | 增加无人机后探索速度如何变化 |
| 计算与通信开销 | Fig. 14 | 随无人机数量增加，规划时间和带宽是否仍可接受 |
| 在线地图时间快照 | Fig. 16、Fig. 17 | 中间时刻和结束时刻的地图、轨迹如何增长 |
| 协同消融表 | Table I | 去掉空间分解、路径优化或负载均衡后的时间与总航程 |
| 路径规划消融表 | Table II | Full 与 NoCP 的时间与路径差异 |
| 协同基线表 | Table III | 不同协同方法在理想/受限通信下的 Avg、Std、Max、Min |

RACER 对每种方法在每个场景运行 5 次，并在公平对比时保持相同的路径规划器、轨迹生成器和动力学参数，只改变协调模块。由此可得：

- 三机论文必须记录每架无人机的轨迹，而不能只记录总轨迹；
- 必须能计算总航程、最长单机航程、路径交叉/重复覆盖和负载均衡；
- 必须记录任务分配与重分配，才能证明协调是在线产生的；
- 若声称适用于受限通信，必须记录实际消息量、带宽、延迟或丢包；
- “三机比单机快”只能证明并行资源有效，不能单独证明协同算法有效。

### 2.3 三维大规模探索与低内存地图

文献：

- J. Huang et al., “Efficient UAV Exploration for Large-Scale 3D Environments Using Low-Memory Map,” Drones, 2024.
- DOI：https://doi.org/10.3390/drones8090443

该文采用：

- 三种不同类型的三维环境；
- 已探索体积随时间变化曲线；
- 不同方法完整轨迹；
- 内存占用随已知空间体积变化曲线；
- 地图更新耗时、总内存、总探索时间、总飞行距离和平均速度表；
- 真实环境中的在线点云地图、探索边界和轨迹。

这说明如果本文将“复杂三维废墟”作为重要卖点，就不能只写尺寸，还要报告可重复的环境复杂度参数，并应保留高度分层或垂直连接区域的完成情况。

### 2.4 多机器人探索评价基准

文献：

- Z. Yan et al., “Metrics for Performance Benchmarking of Multi-Robot Exploration,” IROS, 2015.
- 公开稿：https://yzrobot.github.io/publications/yz15iros.pdf

该文系统定义了：

- Exploration time：达到预定完成条件所需时间；
- Exploration cost：所有机器人路径长度之和；
- Exploration efficiency：单位移动代价获得的新增探索量；
- Map completeness：已探索区域与真值区域之比；
- Map quality：地图正确重叠部分与真值地图之比。

这为本文提供评价框架，但本文是三维占据表面建图，不能直接照搬二维面积公式。本文应在统一体素分辨率和距离阈值下报告三维表面 Recall、Precision、F1，并明确真值只在实验结束后离线使用。

## 3. 本文最终采用的图表

小论文不追求图表数量，而追求证据链完整。主文暂定 7 幅图、4 张表；必要时将多个子图合并。

### 图 1：系统框架与信息边界

内容：

- LiDAR/里程计；
- 在线局部占据地图；
- Frontier 检测；
- 单机规划或多机协调；
- 局部安全轨迹；
- 控制与地图更新闭环；
- 真值 PCD 只连接仿真传感器和离线评价器，不进入规划器。

必须证明：

- 系统没有预设航点序列；
- 没有人工划分运行区域；
- 无人机只知道探索边界，不知道内部废墟结构；
- 目标点由当前在线地图中的 Frontier/任务单元动态产生。

数据需求：无运行数据，但程序接口和 launch 配置必须与图一致。

### 图 2：Ruins-Urban-01 环境与复杂度

子图：

- base、medium、complex 三个固定环境；
- 代表性的未见随机种子环境；
- 侧视图展示局部二层和垂直连接；
- 标注任务边界、起点和尺度，不标注任何预设路线。

必须证明：

- 环境确实包含岔路、环路、死路、窄通道、坍塌结构和高度变化；
- 三个难度等级不是只改变碎石数量；
- 随机环境可复现且可通行。

数据需求：

- 场景种子；
- 任务边界；
- 可观测真值体素数；
- 障碍占比；
- 分支、环路、死路、窄通道和垂直连接数量；
- 最小/平均通道宽度与无人机碰撞直径之比。

### 图 3：在线自主探索过程

采用一个接近中位数的正式运行，固定展示：

- \(t=0\)；
- 达到最终有效覆盖量 25% 的时刻；
- 50% 的时刻；
- 75% 的时刻；
- 结束时刻。

每个快照同时显示：

- 当时的在线地图；
- 截至当时的已执行轨迹；
- 当前 Frontier/在线任务单元；
- 当前被选目标；
- 三机阶段显示每个任务的归属。

必须证明：

- 地图和决策随观测在线增长；
- 中间目标发生变化；
- 路线不是启动前写好的；
- 三机在同一时刻承担不同未知分支。

数据需求：

- 带时间戳的在线地图快照或体素首次发现时间；
- 带时间戳的无人机位姿；
- Frontier/任务单元生成、选择、完成、失效和重分配事件。

### 图 4：探索进度曲线

内容：

- 横轴为仿真时间；
- 纵轴为统一定义的已探索可观测体积或真值表面 Recall；
- 每种方法显示同一组随机种子的均值曲线；
- 阴影表示标准差或 95% 置信区间；
- 单机图比较单机基线与后续单机改进时使用；
- 多机图比较无协调、贪心协调和本文方法。

必须证明：

- 方法在整个过程中获得信息更快，而不是只在最终时刻偶然更好；
- 达到相同覆盖阈值所需时间更短；
- 不同随机环境下趋势稳定。

数据需求：

- 固定频率的 \(C(t)\)；
- \(T_p\)；
- 固定时间预算下的覆盖率；
- 覆盖曲线 AUC。

### 图 5：最终三维地图、轨迹和误差

内容：

- 侧视图或高度分层图，避免俯视投影掩盖垂直结构。

必须证明：

- 最终结果是三维地图；
- 缺失主要发生在哪些不可观测或难通行位置；

## 5. 正式实验矩阵

### P0：工程调试，不进入论文统计

目的：确认系统、数据记录器和离线评价器能完整工作。

- 每个固定场景 1 次；
- 允许发现问题后修改代码和参数；
- 所有运行必须保留，但明确标注 `debug`；
- 当前第一次 base 成功运行属于 P0/E1，只能证明闭环跑通。

### P1：协议校准，不用于方法优劣结论

目的：冻结探索边界、可观测体积、传感器参数、超时、覆盖阈值和误差容差。

- base、medium、complex 各 3 次；
- 只运行单机 FUEL；
- 依据共同可达到水平确定 \(T_p\) 的 \(p\)；
- 校准结束后生成 protocol version 1.0；
- 此后修改任何受控参数都必须提高协议版本并重跑全部方法。

### E1：正式单机基线

- 方法：B1 单机 FUEL；
- 场景：base、medium、complex；
- 每场景 5 个冻结种子；
- 每个种子重复 3 次；
- 合计 45 次；
- 输出图 3--5 的单机部分和表 3 的 B1 行。

若虚拟机运行时间无法承担 45 次，可将主要统计压缩为 3 个 profile × 5 个种子 × 1 次，并对代表场景额外重复 5 次估计方差；但不能只报告一次。

### E2：三机无协调与简单协调基线

- B2：三机独立 FUEL；
- B3：三机最近 Frontier 贪心分配；
- 相同的 complex 与未见随机种子；
- 每个方法使用完全相同的种子和初始位置；
- 每条件至少 5 次；
- 输出图 4、图 6和表 3。

### E3：本文三机协同方法

- M1 与 B2、B3 使用相同底层地图、Frontier 检测、轨迹规划器和动力学；
- 只替换任务效用与协调模块；
- 对每个 seed 使用配对比较；
- 输出图 4、图 6和表 3。

### E4：消融

- A1：去除信息增益；
- A2：去除重复探索惩罚；
- A3：去除负载均衡；
- 每个配置至少 5 个相同种子；
- 输出图 7和表 4。

### E5：通信与故障鲁棒性

- 丢包率：0%、10%、30%；
- 延迟：0、100、300 ms；
- 可选：单机中途退出；
- 每个条件至少 5 次；
- 输出图 7和表 4。

## 6. 正式实验启动门槛

下一次运行只有同时满足以下条件，才能标记为 `formal`：

1. 协议版本、方法、profile、seed 和重复编号已在运行前写入 manifest；
2. 场景与参数文件哈希已生成；
3. 轨迹记录器已验证；
4. 覆盖时间序列记录器已验证；
5. 规划耗时记录器已验证；
6. 最终在线地图自动保存已验证；
7. 失败、超时和碰撞状态能被记录；
8. 固定频率快照或体素首次发现时间已验证；
9. 所有受控变量来自同一冻结配置；
10. 运行结束后可由一个命令生成完整 run 目录并通过完整性检查。

任一项缺失，该次运行自动标为 `debug`，不能补填数据后混入正式统计。

## 7. 当前代码与冻结方案的差距

已经具备：

- 运行时长；
- 单机总路径长度；
- FUEL 完成信号；
- B-spline 和位置命令是否发布；
- 占据地图是否增长；
- 最终在线占据 PCD；
- 最终表面 Recall、Precision 和 F1；
- 规划失败和碰撞重规划日志计数；
- 文件哈希与结果目录。

正式 E1 前必须补齐：

1. `trajectory.csv`：带时间戳的完整位姿；
2. `coverage_timeseries.csv`：固定间隔的在线地图/覆盖进度；
3. `planning_timing.csv`：Frontier、全局、局部和轨迹规划耗时；
4. `system_resources.csv`：CPU、内存、墙钟时间和仿真实时因子；
5. `events.jsonl`：Frontier 选择、完成、失效与重规划事件；
6. 运行前 manifest 与协议版本；
7. 自动完整性检查器。

因此，当前不能立即重复运行正式 base 实验。正确的下一步是先实现并验证以上记录器，然后进行一次 P0 数据完整性演练；通过后才开始 P1 校准。
